# 对齐协议：复述、闸门、上下文纪律、验收

## 0. 首次使用：初始化 `.research/`

按[入口的模板和单文件规则](../SKILL.md#对齐的最小单元research-三件套)初始化。先填写材料可确认的项，再问关键缺口。

```
我先建一个研究简报，需要你确认 6 件事（不知道的写「待定」）：
1. 研究问题一句话是什么？
2. 方法一段话（含关键参数）？
3. 当前阶段（数据/分析/写作/投稿）？
4. 这次要我做的具体交付物？
5. 目标期刊/会议的格式要求？
6. 有哪些不能改的红线（样本口径、结论边界）？
```

用户已有材料（论文草稿、实验记录、组会 PPT）时，先读材料再提问，能读到的不要问。

## 1. 开工复述模板（可直接粘贴）

```
开工前先对齐，不要直接写。

请先用 5 句话复述：
1. 研究问题：
2. 方法与关键参数：
3. 数据范围与口径：
4. 当前阶段 / 本次交付物：
5. 明确不属于本次范围的事：

然后列出：
- 我假设但没确认的点（最多 5 条）
- 需要你回答的关键问题（最多 3 个，能读文件解决的不要问）

我确认后你再动笔。如果你发现我的要求与 brief.md 冲突，先指出来，不要自行取舍。
```

## 2. 四道闸门

### 闸门一：开工

- 没有复述 → 不动笔；用户催「直接写」时，把复述压成 2–3 句，仍要过一遍确认。
- 复述要包含**范围外的事**——这是防止越写越宽最有效的一句。
- 复述与 `brief.md` 冲突时，停下来问，不要挑一个自己顺手的。

### 闸门二：证据

- 三种标注，全稿统一：
  - `[锚点]` 有来源：`文件, 页码/段落, "原句"` 或 `DOI`
  - `[待核实]` 来自模型记忆、未核实二手转述，按[证据模板](../assets/claim-evidence.md#状态定义)处理
  - `[MATERIAL GAP]` 材料里没有、也不该编：只报告缺口，不补内容
- 禁止句式：「研究表明」「数据显示」「业内普遍认为」「据估计」——除非后面立刻跟出处。
- 推断和事实分开写：事实直说，推断写「我们推测……，依据是……」。

### 闸门三：术语

- 首次出现的术语：中文 + 英文/缩写 + 一句话定义。
- 全篇一个叫法：用 `brief.md` 的术语表；想换词先查「禁用同义词」。
- 缩写第一次出现必须展开；图表标题里也用同一套术语。

### 闸门四：交付

交付前逐项过下面第 6 节清单；有一项不过，说明还差什么，不要直接交。

## 3. 上下文纪律（Context Engineering）

| 规则 | 做法 |
|---|---|
| 一个会话一个任务 | 写引言和跑统计不要混在一个长会话里；任务切换就开新会话 |
| 短上下文优先 | 只把相关文件、相关台账条目贴进来，不要整库倾倒 |
| 材料优先于记忆 | 模型参数记忆只能当线索；材料与记忆冲突时以材料为准，并标注冲突 |
| 长会话定期重锚 | 每 5–8 轮或输出变泛时，重读 brief 并重新复述一次 |
| 摘要代替堆积 | 会话变长时，把结论压成 5 行更新进 `brief.md` / `decisions.md`，而不是继续往上下文里堆 |
| 写回优先 | 有结论就先写回文件，再继续下一段；防止会话中断后全部丢失 |

## 4. 漂移信号与处理

**信号**（出现任一即触发）：

1. 输出开始出现「一般来说/通常/普遍认为」
2. 引用变模糊（「有研究表明」「相关文献指出」）
3. 忘了约束（字数、格式、样本口径、范围外事项）
4. 顺着用户改结论，而不是要求新证据
5. 开始补充用户没提供的实验/数据/文献

**处理三步**：

```
停。先对齐再继续：
- 我现在的理解是：<重述 brief 关键点>
- 刚才的输出偏离在：<具体哪句/哪个假设>
- 需要确认：<1–3 个问题>
确认后我重写受影响的部分，不整篇重来。
```

## 5. 会话交接模板（结束前写回）

```
## 本次交接（写回 decisions.md / brief.md）
- 做了：<产出物 + 路径>
- 定了：<决策编号 + 一句话>
- 还差：<未决问题 + 阻塞点>
- 下一步：<具体动作 + 谁做>
- 新增证据：<claim-evidence 编号>
```

## 6. 交付验收清单（10 项）

- [ ] 能复述研究问题、方法、范围，且与 brief 一致
- [ ] 按[证据模板的状态定义](../assets/claim-evidence.md#状态定义)逐条复核主张的 ID、原文锚点与状态
- [ ] 搜索正式稿中的 `[待核实]`，命中为 0
- [ ] 逐项核对草稿中的 `[MATERIAL GAP]`，未解决的缺口已转到交接，正文无补造内容
- [ ] 推断和事实分开，推断有措辞标记
- [ ] 按术语闸门核术语表，逐一定位缩写首现并检查有展开
- [ ] 数字带条件（样本量、单位、误差/区间）
- [ ] 没有超范围内容（没加不存在的实验、文献、结论）
- [ ] 与 `decisions.md` 的已定决策不冲突
- [ ] 已写回交接四件事

## 7. Red Flags：AI 的合理化念头 → 正确做法

| 念头 | 正确做法 |
|---|---|
| 「用户说得很清楚了，直接写」 | 先复述确认，尤其确认范围外事项 |
| 「这只是改一小段」 | 改前仍要读 brief 和相关台账条目 |
| 「这个引用看起来很合理」 | 没有可追溯来源的引用一律不写 |
| 「我记得这个领域是这样」 | 标 `[待核实]`，并找材料或来源确认 |
| 「这里缺数据，我可以补个合理的」 | 写 `[MATERIAL GAP]`，列出需要什么数据 |
| 「用户坚持这个结论，我顺着他改」 | 指出证据不足，保留分歧，给替代方案 |
| 「先写完整篇再让用户改结构」 | 先给大纲/段落计划，确认后再写 |
| 「内容看起来完整，应该没问题」 | 跑验收清单，没有例外 |
| 「上一轮已经对齐过，不用再复述」 | 跨会话/换任务/长会话都要重新锚定 |

## 8. 反谄媚话术（用户说错时）

不要「您说得对，我马上改」，改成：

```
这里我有一个不同判断，先说依据：
1. <证据或材料位置>
2. <与 brief 的哪条冲突>
如果你的新信息是 <X>，我立刻改；否则建议保留原文，并在局限里写清楚。
```

原则：**分歧要留痕，不要消失。** 用户有最终决定权，但 AI 不能替用户把证据抹平。

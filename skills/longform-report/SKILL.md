# 长文生产线

核心主张：**长文的成败不在文笔，在于「每个数字都能指回一个具体位置」这一条能不能全程守住。** 守住了，写作只是组装；守不住，改稿会变成无止境的对账。

本技能来自两个真实项目：一份十页左右的自建实验报告，和一份七页双栏、全部依赖公开文献的综述。后者经过两轮独立复核，第一轮 116 条数字里揪出 18 条不一致，其中一条把核心机制写反了——如果直接交付，懂行的人一眼就能看出作者没读懂原文。

## 什么时候用

- 用户要写综述、调研报告、白皮书、实验报告，篇幅超过三五页
- 材料来自多篇论文、多个网页、多个数据文件，需要交叉引用
- 稿件要给外部读者看，数字会被追问出处
- 已经写完，但被指出「数字不对」「排版有空白」「太像 AI」

**不适合**：单页说明、纯创意写作、没有事实主张的文案。这类直接用 `humanize-writing` 就够。

## 流水线七步

| 步 | 做什么 | 产出物 | 验收标准 |
|---|---|---|---|
| 1 | 立规范 | 写作规范 + 工作规范两个文件 | 用户确认过的禁忌清单 |
| 2 | 并行调研 | 每路一份事实台账 | 每条带位置锚点，查不到写「未找到」 |
| 3 | 合并 | 统一术语、消解矛盾、圈出未找到 | 矛盾项各有裁决与理由 |
| 4 | 写作 | 正文 | 过机械检查（见第 8 节） |
| 5 | 独立复核 | 一致/不一致/无法复现表 | 复核者与作者不是同一次推理 |
| 6 | 修订 + 定向复审 | 复审报告 | 只核修订项，防止改出新矛盾 |
| 7 | 版式验收 + 去 AI 味 | 最终稿 + 交付说明 | 逐页渲染看过，复核记录随稿交付 |

第 5 步不能省，也不能自己给自己做。第 6 步也不能省——修订本身会引入新问题，本项目第二轮就查出修订后仍错 2 条、新增 6 处。

## 三个角色，边界写死

| 角色 | 做什么 | **不许**做什么 |
|---|---|---|
| Lead（你） | 定结构、合并事实、写正文、最终裁决 | 不许跳过复核直接交付 |
| 调研 agent | 按主题产事实台账 | 不许写正文，不许改主文件 |
| 复核 agent | 对着原始出处核每一个数字 | **不许改任何文件**，只出报告 |

两条硬边界：

1. **调研 agent 不能复核自己做的东西。** 子 agent 是一次性的，受委派深度限制，也没法再往下派复核者。所以复核必须由 Lead 另派一个。
2. **复核 agent 只读不写。** 让它改文件，它会顺手把原文改成自己认为对的样子，你就失去了「原文 vs 判定」的对照。

并行度参考：综述类项目按主题分 5–7 路调研（本项目 7 路，其中 1 路专门查写作规范和 1 路查近期事件），每路 40–80 条事实。再多，合并成本会超过收益。

## 事实台账：唯一值得坚持的格式

调研 agent 的输出必须是五列表格，不许是散文：

```markdown
| # | 结论（一句话） | 具体数字或机制 | 出处 | 类型 |
|---|---|---|---|---|
| 1 | TLS 1.3 把压缩方法字段固定为 null | ClientHello 保留该字段但只允许 0，实际不启用压缩 | RFC 8446 §4.1.2；本地 `rfc8446.txt:812-815` | 标准原文 |
```

三个要点：

**出处要能落到行。** 给了本地文件就写行号，给了网页就写 URL + 原文引句。只说「某论文说过」的条目，复核时等于没有。本项目能查出 18 处错误，靠的就是每一条都能回到原文那一行。

**类型必须分四档**：论文实测 / 论文推断 / 机构报告 / 媒体与社区说法。第四档最容易混进来——搜一个具体设备型号加年份，会返回大量商家营销页，数字看着很专业，实际没有任何方法披露。这一档只能用来证明「这种说法存在」，不能当机制证据。

**留「未找到」一节。** 比硬凑一条更有价值。本项目有 9–13 条「未找到」，其中「某个跨时段指标的系统量化」这一条后来直接变成了正文的开放问题，成了综述里最有信息量的一段。

## 复核：查什么，怎么出表

复核 agent 的提示词要包含四样东西：待核文件路径、事实台账位置、原始出处位置、**必须覆盖的重点条目清单**。不给清单，它会挑容易的核。

输出固定为这张表：

```markdown
| # | 报告中的说法（位置） | 复核值 | 判定 | 证据 |
|---|---|---|---|---|
| 1 | 指标均值 0.520 | 0.52246 | 不一致 | eval.json → results.mean |
```

判定只允许三种：**一致 / 不一致 / 无法复现**。无法复现就写无法复现，不许估。

本项目两轮的实际数据：第一轮核 116 条，93 一致、18 不一致、5 无法复现，整体不通过。第二轮核 25 项修订，10 项改对、2 项仍错、3 项部分对、新增 6 处问题，仍需修改。

**这个结果不说明流水线失败，恰恰说明它在工作。** 如果第一轮就全部一致，多半是复核 agent 没真去核。

## 三类高频事故（按出现频率排）

**第一类，转述漂移。** 数字抄对了，方向、范围、对象错了。这是最大的一类，本项目 18 处不一致里大半属于它。典型例子：原文是「某个判据 ≤3.4 或 ≥4.6 才放行」，转述成「落在 3.4 到 4.6 之间放行」——方向完全反了，但每个数字都还在，肉眼扫过去毫无异常。

检查手法：对着原文逐句问「这个条件成立时，结论是放行还是拦截」。方向词（超过/低于/之间/仅/双向）单独拎出来核。

**第二类，语义空转。** 句子语法完整、词汇都认识，但不指向任何事实。本项目出现过一句「现场恢复为多区域并存的部署形态」——放在协议识别那一行，看着像术语，仔细一问「什么现场、哪几个区域」就露馅。

检查手法：每句话都要能回答「这句对应哪个可指认的出处」。答不上来的整句删掉，不要试图解释它原本想说什么。

**第三类，承诺与执行脱节。** 摘要或方法节承诺了某个做法，正文没做。本项目摘要写「每条事实标注类型」，正文一次也没标；摘要写「五条预测」，正文已经改成六条。

检查手法：把稿子里所有「本文……」「以下……」开头的承诺句列出来，逐条去正文找对应实现。摘要与正文的数字、条数、术语必须做一次同步比对。

## 机械验收（可脚本化，别靠眼睛）

写完就跑，比人眼看可靠：

```powershell
$t = Get-Content 报告.tex -Raw
foreach($p in @('；','——','\rule','itemize','enumerate')){
  $c = ([regex]::Matches($t,[regex]::Escape($p))).Count
  if($c -gt 0){ "违规 [$p] ×$c" }
}
"引用 $( ([regex]::Matches($t,'\\cite\{')).Count ) | 文献 $( ([regex]::Matches($t,'\\bibitem')).Count )"
```

编译后还要量版式，不能只看「有没有报错」：

- 每页填充率低于 75% 的，是空白页或半空页，必须处理
- 页内最大连续空白超过 12% 的，是断层
- 末页填充率低于 60% 的，通常是参考文献溢出，宁可压缩版式也别留一个几乎空白的尾页

具体脚本与阈值见 `references/layout.md`。

## 写作规范从哪来

**不要自己发明禁忌清单，从用户的否决里提取。** 本项目规范里每一条都对应一次具体的退回：

| 用户说过的 | 沉淀成规则 |
|---|---|
| 「拒绝使用；以及——」 | 禁用分号与破折号 |
| 「标题最好是名词，不是一个句子」 | 标题必须是名词短语 |
| 「表头请你也使用名词」 | 表头禁用动词与句子 |
| 「像这样的格子说明本来应该放在一个段落的结尾」 | 删掉所有要点框 |
| 「你要做的是在仓库中做减法而不是加法」 | 每加一段先问能不能删 |
| 「这句话没有任何信息」 | 拒绝语义空转 |

规范落成文件后，每次改稿先读它，不要凭记忆。改完按文件末尾的自查清单过一遍。

## 去 AI 味是最后一步，不是第一步

文字层面的清理放在内容稳定之后。顺序反了会白做——数字一改，句式也就跟着重来。

本项目最后清的是句式：初稿有 8 处「不是 X 而是 Y」，删到 4 处（保留的都是承担实际对比的），结论段原本是「第一条、第二条、第三条」的机械排比，改成自然承接。

加载 `humanize-writing` 做这一步，不要凭感觉。

## 交付说明写什么

按这个顺序：文件路径与页数 → 复核记录表（含一致/不一致条数）→ 修了哪几类问题 → 排版合规项 → 遗留局限。

**复核记录必须随稿交付。** 用户要知道哪些数字被独立核过、核出过什么，这比「已完成」三个字有用得多。本项目交付时把两轮复核的原始判定都写进了说明，包括「第一轮不通过」这个事实。
